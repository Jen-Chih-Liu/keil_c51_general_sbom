# 概念解說：為何標準 8051 專案必須採用編譯產物逆向 SBOM？

本篇概念解說深入探討為什麼傳統軟體組成分析（SCA）工具在裸機標準 8051 專案上會徹底失效，以及本專案為何選擇「以編譯與連結產物（Build Evidence）逆向重構 SBOM」的架構路徑。

---

## 1. 傳統 SCA / SBOM 工具的根本盲點

現代主流的軟體組成分析工具（例如 Syft、Trivy、Black Duck、Snyk、cdxgen 等）都是圍繞著現代軟體開發生態圈打造的。它們的運作依賴明確的「套件清單（Manifests）」或「鎖定檔（Lockfiles）」：
- JavaScript: `package.json`, `package-lock.json`
- Python: `requirements.txt`, `Pipfile.lock`
- Rust / Go: `Cargo.lock`, `go.mod`
- C/C++: `conan.lock`, `vcpkg.json`, `CMakeLists.txt`
- 現代嵌入式 Cortex-M: CMSIS-Pack (`.pdsc`)

### 傳統 8051 裸機專案的真實環境
但在工業控制、家電、車載輔助微控制器等領域，大量運作的是經典的 8051 晶片（如 Winbond / Nuvoton W78 系列）。這類專案具有極為鮮明的特點：
1. **完全零套件管理清單（Zero Manifest）**：工程師開案時，只建立了 `.uvproj`，加入 `STARTUP.A51` 與幾個 `.c` 檔。
2. **完全沒有外部 BSP 或開源框架**：程式碼中僅寫了 `#include <REG52.H>` 或 `<REG51.H>`。
3. **編譯器自帶封閉二進位庫**：Keil C51 的標準函式庫是預先編譯好的二進位封裝檔（`C51S.LIB`、`C51C.LIB`、`C51L.LIB` 等）。

若直接將 Trivy 或 Syft 指向這樣的目錄掃描，它們**完全找不到任何相依性元件**，最後輸出一個空的清單。

---

## 2. 偽「零相依」與真實合規風險

在資安合規（例如歐盟網路韌性法案 Cyber Resilience Act, CRA，以及美國行政命令 EO 14028）的視角下，韌體並不是真的「零相依」：
- **韌體燒錄檔包含他人編寫的程式碼**：即使韌體工程師沒有寫任何動態記憶體分配或除法演算法，只要在 C 語言中寫了 `a / b`（16 位元除法）或宣告了全域變數初始值，Keil Linker 就會偷偷把閉源的 `C51S.LIB` 內建副程式複製進晶片的 Flash 記憶體中。
- **編譯器與標頭檔的供應鏈風險**：標頭檔 `REG52.H` 定義了暫存器位址，標頭檔的瑕疵或工具鏈的漏洞同樣直接威脅韌體行為。
- **不可追溯性**：若交付出去的產品僅有一包 HEX 檔，日後遇到資安弱點稽核時，將無法證明該 HEX 是由哪個版本的編譯器產出、使用了哪些版本的執行期函式庫。

---

## 3. 解決方案：基於建置證據的逆向提取

既然原始碼目錄沒有 Manifest，答案就藏在**編譯產物（Build Evidence）**中：

```text
[原始碼掃描 (失敗)]  --> 找不到 package.json --> 輸出空白 SBOM (不合規)

[建置證據提取 (成功)] 
 ├── 解析 .uvproj       --> 獲得目標 MCU 硬體規格與供應商 (W78E052D)
 ├── 解析 .lst & Header --> 獲得實際引用的標頭檔與版權宣告 (REG52.H, INTRINS.H)
 ├── 解析 .m51 Map 檔   --> 獲得 Linker 隱性打包的 C51S.LIB 與內部模組
 └── 解析 TOOLS.INI     --> 獲得發布套件版本與個別編譯器執行檔 SHA-256
      │
      ▼
 輸出標準 CycloneDX 1.5 & SPDX 2.3 SBOM (完整可追溯、資安合規)
```

透過這種方式，我們將原本不可見的「隱性相依性」顯性化，使經典 8051 專案無需強加現代套件管理系統，也能輕鬆具備符合現代資安法規的 SBOM 產出能力。
